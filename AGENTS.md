# Oura AI Connector: правила работы

## Источники и границы

- Исходный продуктовый план: `oura-ai-connector-mvp.md`. Очередь и критерии приёмки: `TASKS.md`. Текущее состояние и точка продолжения: `PROGRESS.md`.
- MVP: Oura → удалённый MCP → ChatGPT, четыре инструмента, нормализация, минимальная упаковка и публичные страницы. Не добавлять UI/dashboard, отдельную AI-модель, аналитику, оплату, фоновые синхронизации или другие устройства.
- Предположения плана про OAuth, scopes, ограничения Oura и требования публикации проверять по актуальной официальной документации. Сохранять ссылки и дату проверки в документах проекта.
- Не передавать upstream OAuth-токены через MCP без доказанной совместимости с требованиями audience/resource и запретом token passthrough. Не объявлять интеграцию работающей только на основании fixtures.
- Не сохранять реальные health payloads и секреты в Git, документации или логах. Для тестов использовать явно синтетические данные.

## Исполнитель и ревьюер

- Реализацию выполняет подагент **`gpt-6-luna` с `reasoning_effort=xhigh`**. Пользователь явно выбрал эту модель; не заменять её молча.
- Основной агент остаётся планировщиком и ревьюером. Он поручает Luna одну текущую задачу или исправления по ней, проверяет diff и значимые проверки, фиксирует решение о приёмке. Не принимает собственную реализацию вместо Luna.
- Использовать подагентов текущего чата, а не создавать отдельные пользовательские чаты. Один исполнитель за раз; задачи идут по зависимостям.
- Luna не меняет критерии приёмки и не отмечает задачу принятой. Она может выставить `in_progress`, `needs_review` или `blocked`; только ревьюер выставляет `done`.
- После запуска первой задачи по текущему поручению завершить её ревью и сохранение. Следующие задачи запускать по дальнейшему поручению пользователя.

## Каждая итерация сохраняется

1. Перед работой прочитать `AGENTS.md`, `TASKS.md`, `PROGRESS.md`, `git status --short`, последние коммиты и незавершённый diff. Не перезаписывать чужие изменения.
2. В `PROGRESS.md` до изменений записать ID задачи, состояние, выбранный следующий шаг и фактические параметры исполнителя.
3. Итерация — небольшой законченный шаг внутри одной из пяти задач. После каждого такого шага обновить `PROGRESS.md`: сделано, проверки и результаты, известные ограничения/блокеры, точный следующий шаг. Не ждать окончания всей большой задачи. При длинной работе сохранять промежуточную точку не реже чем через 15 минут и перед внешними ожиданиями.
4. Сохранить код и журнал отдельным Git-коммитом: `chore(T1): checkpoint ...`, `feat(T2): ...`, `fix(T3): ...` и т.п. Коммит checkpoint может содержать незавершённую работу; явно указать, какие проверки ещё не прошли. Не включать посторонние файлы. Не переписывать историю.
5. Перед передачей ревьюеру записать `needs_review`, команды проверок и результаты, список существенных изменений, ограничения и следующий шаг. На ревью исправления выполняет тот же исполнитель Luna xhigh и снова сохраняет checkpoint.
6. Ревьюер после проверки фиксирует результат в журнале и отдельным коммитом. `done` допустим только при выполненных критериях. Внешняя проверка, которую не удалось провести, остаётся явно незавершённой.
7. При известной остановке по лимитам/ошибке сначала сохранить всё возможное и точку продолжения. Внезапную остановку нельзя предсказать: при возобновлении сверить журнал с Git и незакоммиченными изменениями, восстановить фактическое состояние и продолжить, а не начать заново.
8. Для продолжения достаточно поручения «продолжи по PROGRESS.md». Поднять нового подагента Luna xhigh, если прежний недоступен, с текущим ID и ближайшим шагом. Если осталось ревью, сначала выполнить его. Автоматический запуск после сброса лимитов не настроен.

## Проверки и внешние действия

- TypeScript, небольшой MCP SDK, минимальный сервер. Выбирать и фиксировать версии после проверки документации; не добавлять зависимости без нужды.
- Проверять существенное поведение: протокол MCP, авторизация, изоляция пользователей, диапазоны/даты/часовые пояса, нормализация, ошибки upstream, отсутствие чувствительных данных в логах. Не писать тесты только ради покрытия.
- Если нужны Oura application credentials, домен, hosted auth или reviewer account, сначала подготовить конкретные инструкции/артефакты, затем сообщить, каких данных или действий пользователя не хватает. Не просить секреты в чат; использовать локальное окружение или secret manager.
- Реальный деплой, расходы, отправка заявки, публичная публикация и приглашение тестеров требуют отдельного поручения. До него подготовить проверяемые артефакты и инструкции. Не выдавать локальную готовность за production/beta.

## Clean up task-created temporary files

After every task, delete all temporary scripts and helper files you created solely to complete that task, locally and on remote hosts. This includes one-off Python/shell/JS scripts, probes, scratch files and temporary validation copies. Prefer stdin or inline commands when a saved script is unnecessary. Track your temporary paths and verify their removal before reporting completion, including after failures. Preserve requested deliverables, implementation code, installed integrations and pre-existing user files. Do not leave new temporary scripts behind while cleaning up earlier ones.
